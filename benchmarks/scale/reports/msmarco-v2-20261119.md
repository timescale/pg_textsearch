# MS MARCO passage v2: full-corpus baseline

The corpus contains **138,364,198 passages**, not a reduced performance
sample. All 70 archive members were converted and indexed. This is a
single-pass evaluation with fixed warmup, not a relevance benchmark or
a claim about every deployment.

This is the original high-memory, ParadeDB v0.26.8 baseline, not the
expanded TIN-scenario campaign. It omits several query mixtures and does
not reproduce TIN's 8-vCPU, 32-GB query resource limits.

## Configuration

The host was an Azure `Standard_L32as_v3`: 32 logical CPUs, 256 GiB RAM,
four local NVMe devices in RAID0. Databases had CPUs 0-23,
192 GiB, and 32 GiB `shared_buffers`. The driver used CPUs 24-31.
The 18-24 GB indexes fit in memory; this is not an out-of-cache I/O test.

| Component | Pin |
|---|---|
| pg_textsearch | `8923a5ba16df2731627dfbde6f6e3b62e5b8273b` |
| Native build | GCC 12.2, `-O2`, assertions off; verified installed binary |
| ParadeDB | Official `v0.26.8-pg18`, image digest recorded in artifacts |
| PostgreSQL | 18.7; Debian 12/native and Debian 13/ParadeDB images |
| Benchmarker | `4b262c05af138991d3bf28c683a0fc6b7f113df3` |
| k6 | 1.8.0 with the benchmarker's database extension |

The native source pin was latest main when built.
Only `body` was searched. Both configurations requested English stemming
and stopwords, BM25 `k1=1.2`, `b=0.75`; analyzers are not identical.
Each cell had 60 seconds of excluded search warmup and five measured
minutes. Engines ran sequentially, not against one another's resource
usage. No planner paths were forced.

The natural pack contains all 8,184 official dev1/dev2 queries.
The span pack has 100 queries at each length 2-15, sampled from 2,000
deterministically selected document rows across the full corpus.
These are consecutive normalized word tokens, not necessarily verbatim
substrings under every engine's tokenizer. Lengths are interleaved.
Time-limited closed-loop cells can cover different query prefixes;
these are not paired, fixed-count per-query trials.

## Boolean and count workloads

### Subsequent plan investigation

Two independent causes were reproduced on the full corpus:

- The native AM deliberately disables a path that combines a Boolean
  index condition and ranked ordering. Separating these into distinct
  query levels allows an indexed plan without changing the extension.
- Boolean-only costing uses a fixed 10% index selectivity. At this scale
  its estimated random heap-fetch cost can exceed a sequential scan,
  even for a query with very few matches. A typed query parameter alone
  does not solve this. Setting `random_page_cost=1.1` for the NVMe host
  restored the native Boolean index path in the full-corpus probes.

The expanded campaign applies that cost setting and custom parameter
plans equally to both engines, and audits every native query's plan.
It does not disable sequential scans. These are separately labeled
tuned runs, not replacements for the baseline below.

Both exact manual ranking shapes were checked against an independent
Boolean-filtering/standalone-scoring oracle. `rank_first` can stop early
when enough matches rank highly, but can exhaust a very large OR stream
when fewer than ten documents match. `filter_first` avoids that trap by
ranking every Boolean match; broad filters may therefore still be costly.
Empty analyzed Boolean filters are short-circuited to zero matches,
rather than scanning the corpus. No arbitrary candidate truncation or
planner-hook change is used.

Full-corpus probes confirmed that manual rewrites can recover indexed
AND/phrase execution, but a long OR count still exceeded its 30-second
probe deadline even with an index scan. Indexed execution is necessary
here, not a guarantee of competitive performance.

### Original baseline results

All 20 native conjunction, phrase, and count cells failed their measured
error thresholds under the 60-second request budget. Their finite
successful-subset latencies are not reported as benchmark results.
Captured plans showed sequential scans for the default combined
Boolean/ranked paths; this is a planner/execution-path gap, not evidence
that native Boolean syntax is unsupported.

quoted `@@@` parser each returned one. The actual driver reproduced the
failure and passed after switching to quoted parser input. ParadeDB
v0.27.0 passed both forms on a stronger three-row fixture; compare the
[released builder](https://github.com/paradedb/paradedb/blob/v0.26.8/pg_search/src/query/pdb_query.rs#L1788)

No duplicate engine fix was proposed.

A separate corrected phrase run was started against an offline clone,
but superseded before completion by the expanded campaign on ParadeDB
v0.27.0. No competitive phrase timings are published from the incomplete
supplement. Original database volumes and run artifacts remain preserved.

## Indexed updates plus top-10 reads

The requested write rate was 1,000 updates/second. Writers toggled an
indexed-text suffix over 100,000 evenly spaced document IDs; this is a
hotset workload, not uniform random updates over 138 million documents.
There were 32 preallocated writers and at most 64. Search warmup preceded
the measured write load. Bodies were restored and vacuumed between cells.

PGTS denotes pg_textsearch; PDB denotes ParadeDB.

|---|---:|---:|---:|---:|---:|
| Natural | 1 | 14.80 | 204.98 | 9.87 | 122.88 |
| Natural | 8 | 56.11 | 388.26 | 13.92 | 1681.41 |
| Spans | 1 | 6.59 | 435.21 | 9.54 | 135.22 |
| Spans | 8 | 25.80 | 718.53 | 10.71 | 2329.43 |

| Pack | Readers | PGTS updates/s | PDB updates/s |
|---|---:|---:|---:|
| Natural | 1 | 891.45 | 1000.00 |
| Natural | 8 | 700.83 | 999.31 |
| Spans | 1 | 800.61 | 1000.00 |

**These are not equal achieved-write-load comparisons.** Native dropped
scheduled writes and delivered 525-891 updates/s with this client cap.
ParadeDB delivered approximately 1,000/s, with 189/218 dropped arrivals
in the eight-reader natural/span cells and none in the one-reader cells.
Neither engine reported SQL update failures. These observations do not
establish either engine's unconstrained maximum write throughput.

## Lead and functional validation

Lead is an intentionally non-production, full-heap implementation.
Its published image is deliberately a debug build; it is not a TIN
performance proxy. The default 10K-row compatibility check and the
separate full-corpus bounded control are recorded separately.

The corrected 10K-row compatibility matrix completed all eight cells.
The separate control loaded **all 138,364,198 rows** in 244.37 seconds,
with a 133.13-second index/post phase. Both full-corpus result probes
exceeded their 30-second budgets, and all eight disjunction cells failed
their measured error thresholds under 60-second request budgets. No finite
successful-subset performance figures are reported for these failed cells.
This result characterizes the published Lead prototype, not PlanetScale TIN.

Result probes capture IDs/counts for one natural query and one 15-word
span per supported family. They are not judged relevance evaluations.
Native completed two disjunction probes; six Boolean/count probes
exceeded their 30-second budgets. Driver success alone does not establish
matching phrase semantics.

## Native optimization priorities

The largest functional gap is the default Boolean/ranked and count path:
all 20 cells exceeded their request budgets. An integrated filtered
ranking path would matter more here than a small disjunction-QPS gain.
Build profiling should explain the roughly 4.9x index/post gap. The
long-span curve and native read tails warrant scoring profiles, while
mixed-load work should investigate achieved write pressure and stalls,
not optimize search QPS by allowing more scheduled writes to drop.

## Reproduce the aggregate statistics

The [CSV](msmarco-v2-20261119.csv) contains all 64 production-driver cells,
including failed ones and both client counts. The eight unverified
ParadeDB phrase cells have `status=invalid_semantics` and blank timings.
An `ok` status is not a relevance or semantic certification.
Pilot runs are excluded.

```bash
python3 benchmarks/scale/summarize.py \
  benchmarks/scale/artifacts/runs/msmarco-20261119-v1 \
  --engine pg_textsearch --engine paradedb > measurements.csv
```

Percentiles are computed from raw search samples, not averaged per-query
percentiles. k6 iteration counts also include collectors and writers and
are not search QPS. Elapsed intervals include the latest response
timestamp: the pinned dashboard's inactivity detector can otherwise
freeze `endTime` and inflate mixed-workload QPS
([paradedb/benchmarker#115](https://github.com/paradedb/benchmarker/pull/115)).
All successful-cell search counts were reconciled against independent
k6 counters. Raw licensed text, query packs, and infrastructure identifiers
are not included in this report.

### Repeat the full-corpus Lead control

After normal setup/preparation, on the idle benchmark host, the following
reuses immutable shards and the explicit-OR Lead query packs. It runs only
Lead in a new run directory; it does not truncate the corpus to 10K rows.
Nonzero completion from failed cells is intentional and leaves artifacts.

```bash
cd /opt/searchbench/pg_textsearch
MSMARCO_ACCEPT_TERMS=1 \
  /srv/searchbench/pg_textsearch-scale/venv/bin/python - <<'PY'
import os
from pathlib import Path
import shutil
from benchmarks.scale.run import Runner, build_plan, validate_storage

root = Path("/srv/searchbench/pg_textsearch-scale")
build_plan(smoke=False, accept_terms=os.environ.get(
    "MSMARCO_ACCEPT_TERMS") == "1")
validate_storage(root, smoke=False)
runner = Runner(Path.cwd(), root, False, "lead-full-repeat",
                "msmarco-v2", None)
runner._prepare_lead_subset()
sample = runner.lead_dataset
runner.lead_dataset = root / "msmarco-v2-lead-full-control"
data = runner.lead_dataset / "data"
data.mkdir(parents=True, exist_ok=True)
shards = sorted((runner.dataset / "data").glob("*.parquet"))
assert len(shards) == 70
for source in shards:
    target = data / source.name
    if target.exists():
        assert target.samefile(source), target
    else:
        os.link(source, target)
shutil.copyfile(runner.dataset / "manifest.json",
                runner.lead_dataset / "manifest.json")
(runner.lead_dataset / "k6").mkdir(exist_ok=True)
for name in ("natural.json", "spans.json", "matrix.json"):
    shutil.copyfile(sample / "k6" / name,
                    runner.lead_dataset / "k6" / name)
runner.engine("lead")
PY
```

New normal ParadeDB runs already use the corrected phrase protocol, so
their phrase cells do not require a separate historical supplement.
